# Documentación al grano

Escribe para que la persona pueda entender, decidir o hacer algo y seguir trabajando.
Mantén la documentación del proyecto en inglés; esta skill puede estar en español.

## Criterio

- Empieza por lo que necesita el lector: qué hacer, qué ocurre o qué límite importa.
- Usa palabras comunes, verbos directos y párrafos cortos. Tono casual, cercano y
  humano, sin solemnidad, humor forzado ni introducciones de libro.
- En presentaciones del producto y README, destaca beneficios concretos con marketing
  discreto y respaldado por hechos. Evita superlativos, promesas y comparaciones sin
  evidencia. En guías y referencias, prioriza la información práctica.
- Cada dato tiene un lugar de referencia. Enlázalo desde otros documentos;
  no repitas instrucciones, valores por defecto ni explicaciones.
- Usa tablas para comparar opciones o consultar campos y valores. Usa pasos para
  secuencias. Un párrafo basta para una idea; no lo conviertas en una tabla.
- Añade ejemplos sólo cuando aclaren cómo usar algo. Elige el mínimo que funcione.
- Conserva prerrequisitos, límites y advertencias que cambian una decisión o evitan
  errores. Ser breve no significa omitir lo necesario ni escribir como un telegrama.
- Comprueba las afirmaciones contra código, pruebas o fuentes oficiales. Distingue
  lo soportado, lo probado y lo pendiente; no prometas paridad sin evidencia.
- Edita el documento que ya corresponde. Divide por responsabilidad sólo cuando
  facilite encontrar o mantener la información; no crees archivos por costumbre.

## Antes de entregar

Quita frases que no aporten una acción, un dato, un beneficio concreto o una aclaración necesaria.
Revisa enlaces, comandos y consistencia con las referencias existentes.
No añadas un resumen que repita lo que el lector acaba de leer.

Ejemplo de tono:

- Evitar: “In order to take advantage of this functionality, it is necessary to install the runtime beforehand.”
- Preferir: “Install the runtime before invoking the function.”
